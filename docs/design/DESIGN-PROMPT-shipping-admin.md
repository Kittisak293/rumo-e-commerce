# Design prompt — RUMO Admin จัดการการจัดส่ง

> ก๊อปทั้งไฟล์นี้ไปวางใน Claude Design ได้เลย

---

ออกแบบหน้า **admin สำหรับจัดการการจัดส่ง** ของ RUMO (เว็บ e-commerce หลายผู้ขาย, ภาษาไทย)
เป็นส่วนต่อจากหน้าฝั่งลูกค้าที่ออกแบบไว้แล้วใน `RUMO Shipping Tracking Standalone.html`
(รายการคำสั่งซื้อ / รายละเอียดคำสั่งซื้อ / ติดตามพัสดุ) — ใช้ภาษาภาพชุดเดียวกัน ไม่ต้องคิดธีมใหม่

## สมมติฐาน layout

- **Desktop 1280px** — มี chrome เดิมของแอป: header ม่วง `#6d28d9` สูง ~56px + drawer ซ้าย 220px พื้น `#e0e0e0` → **พื้นที่เนื้อหาจริง 1060px**
- **Mobile 390px** — drawer ปิด
- หน้า admin เข้าจากเมนูโปรไฟล์ (ไม่ได้อยู่ใน drawer หลัก) — ใน mockup ใส่ chrome เดิมได้เลย

## ข้อมูลที่มีจริง (ห้ามใส่ฟิลด์ที่ไม่มีในนี้)

```
Order        orderNumber, status(9 ค่าข้างบน), total, totalQuantity, subtotal,
             createdAt, updatedAt
User         name, email
Address      fullName, phone, subdistrict, district, province, postalCode
OrderItem    product.name, product.imageUrl, price, quantity, lineTotal
Shipment     trackingNumber, status(7 ค่าล่าง), lastLocation,
             estimatedDeliveryAt, createdAt, carrier
ShipmentEvent status(7 ค่าล่าง), description, location(ว่างได้), occurredAt
Carrier      name, code, website, trackingUrlTemplate, isActive
```

**ShipmentStatus 7 ค่า:** `pending` `picked_up` `in_transit` `out_for_delivery` `delivered` `failed` `returned`

**ข้อจำกัดที่ต้องเคารพ (อย่าออกแบบสิ่งที่ข้อมูลไม่รองรับ):**
- ไม่มีฟิลด์ `deliveredAt` — วันที่ส่งถึงต้องอ่านจาก `ShipmentEvent` ที่ status = `delivered`
- **`OrderItem` ไม่มีการผูกกับ `Shipment`** → ตอบไม่ได้ว่าสินค้าชิ้นไหนอยู่กล่องไหน
  ถ้าออกแบบ UI แยกของลงหลายกล่อง ให้ทำเป็น **variation แยก** พร้อมหมายเหตุว่าต้องเพิ่ม field ก่อน
- ไม่มีโลโก้ขนส่ง (มีแค่ชื่อ+code) — ใช้ตัวอักษรย่อในวงกลมแทนได้
- ไม่มีระบบผู้ขายรายร้าน — admin เห็นทุกออเดอร์รวมกัน

## บริบทสำคัญ: ระบบนี้เป็นแบบ "คีย์มือ" ไม่ได้ต่อ API ขนส่ง

ในระบบใหญ่ (Shopee/Lazada) พัสดุถูกอัปเดตอัตโนมัติจากการที่พนักงานขนส่ง**ยิงบาร์โค้ด**ตามจุดต่างๆ
แล้วส่งเข้ามาทาง webhook — ไม่มีมนุษย์พิมพ์เอง

RUMO ยังไม่ได้ต่อ API ขนส่ง **แอดมินจึงเป็นคนคีย์เหตุการณ์เองจากใบเสร็จ/หน้าเว็บขนส่ง**
งานออกแบบนี้ต้องทำให้การคีย์มือรู้สึกเหมือน "**บันทึกสิ่งที่เกิดขึ้นจริง**" ไม่ใช่ "แต่งเรื่องขึ้นมา" —
เช่นมี preset ของเหตุการณ์มาตรฐานให้กดแทนการพิมพ์ใหม่ทุกครั้ง (ดูข้อ 3)

**จุดสแกนมาตรฐานของพัสดุจริง 1 กล่อง มีแค่ 6 จุด** — ใช้เป็น preset:

| ลำดับ | ShipmentStatus | ข้อความตัวอย่าง |
|---|---|---|
| 1 | `pending` | ผู้ขายเตรียมพัสดุเรียบร้อย รอขนส่งเข้ารับ |
| 2 | `picked_up` | ขนส่งเข้ารับพัสดุแล้ว |
| 3 | `in_transit` | พัสดุออกจากศูนย์กระจายสินค้า |
| 4 | `in_transit` | พัสดุถึงศูนย์คัดแยกปลายทาง |
| 5 | `out_for_delivery` | พนักงานกำลังนำจ่าย |
| 6 | `delivered` | ส่งถึงผู้รับเรียบร้อย |

# หน้าจอที่ต้องออกแบบ

## 1. คิวงานจัดส่ง (หน้าหลัก)

ตารางออเดอร์ที่แอดมินต้องลงมือ เรียงงานเก่าสุดขึ้นก่อน (ค้างนานสุด = เร่งด่วนสุด)

- แท็บกรอง: `ต้องจัดส่ง` (paid) / `กำลังส่ง` (shipped+shipping) / `ส่งถึงแล้ว` / `ทั้งหมด` พร้อมตัวเลขนับ
- คอลัมน์: เลขคำสั่งซื้อ · ลูกค้า (ชื่อ+อีเมล) · วันที่สั่ง + **ค้างมากี่วัน** · จำนวนชิ้น · ยอดรวม · badge สถานะ · เลขพัสดุ (ถ้ามี) · ปุ่มลงมือ
- ปุ่มลงมือเปลี่ยนตามสถานะ: `paid` → **สร้างพัสดุ** (ปุ่มหลัก) · `shipped`/`shipping` → **บันทึกเหตุการณ์** · `delivered` → ดูอย่างเดียว
- ออเดอร์ที่ค้างเกิน 2 วัน ให้เด่นขึ้น (นี่คือ SLA จริงของตลาด — ผู้ขายมีเวลา 2 วันทำการ)

**ขอ state:** desktop 1280 · mobile 390 · loading (skeleton รูปทรงเดียวกับตาราง ไม่ใช่ spinner กลางจอ) · empty (เคลียร์งานหมดแล้ว — ให้รู้สึกดี ไม่ใช่รู้สึกว่าพัง) · error

**ขอ variation:** ตารางแน่นๆ vs การ์ดต่อแถว — อันไหนอ่านง่ายกว่าเมื่อมี 30 ออเดอร์ และอันไหนรอดที่ 390px

## 2. สร้างพัสดุ

ฟอร์ม: เลือกขนส่ง · เลขพัสดุ · ตำแหน่งเริ่มต้น (ไม่บังคับ) · วันที่คาดว่าจะถึง (ไม่บังคับ)

**สิ่งที่สำคัญที่สุดของหน้านี้:** กดยืนยันแล้ว **ระบบส่งอีเมลหาลูกค้าทันทีและย้อนกลับไม่ได้**
ต้องออกแบบให้แอดมินรู้ตัวก่อนกด — ไม่ใช่แค่ข้อความเล็กๆ ใต้ปุ่ม ลองเสนอ 2-3 วิธี
(preview อีเมลย่อ / แถบเตือน / ปุ่มสองจังหวะ) แล้วบอกว่าอันไหนดีกว่าเพราะอะไร

ควรโชว์บริบทออเดอร์ (ใครสั่ง ที่อยู่ปลายทาง มีอะไรบ้าง) คู่กับฟอร์ม เพื่อกันคีย์ผิดคน

**ขอ state:** ว่าง · กรอกครบ · error รายฟิลด์ (เลขพัสดุซ้ำ/ว่าง) · กำลังส่ง · สำเร็จ · mobile
**ขอ variation:** dialog กลางจอ vs panel เลื่อนจากขวา (slide-over)

## 3. บันทึกเหตุการณ์พัสดุ

ครึ่งบน = timeline ที่บันทึกไปแล้ว (ใช้ดีไซน์ timeline เดียวกับหน้าลูกค้า จุด 16px `#8e4dff` + เส้น 2px `#e5e7eb`)
ครึ่งล่าง = ฟอร์มเพิ่มเหตุการณ์ใหม่

- **preset 6 ปุ่มตามตารางจุดสแกนด้านบน** กดแล้วเติม status + ข้อความให้อัตโนมัติ แก้ต่อได้
- ฟิลด์: สถานะ (7 ค่า) · รายละเอียด · ตำแหน่ง (ไม่บังคับ) · เวลาที่เกิดเหตุการณ์ (default = ตอนนี้ แต่แก้ย้อนหลังได้ เพราะแอดมินมักคีย์ตามหลัง)
- ถ้าเลือกสถานะที่จะ**เลื่อนสถานะออเดอร์อัตโนมัติ** (`picked_up`/`in_transit`/`out_for_delivery` → กำลังจัดส่ง, `delivered` → ส่งถึงแล้ว) ต้องบอกล่วงหน้าในฟอร์ม
- บันทึกแล้ว timeline ข้างบนอัปเดตทันทีโดยไม่ปิดฟอร์ม (แอดมินมักคีย์ทีเดียวหลายรายการ)

**ขอ state:** timeline ว่าง (พัสดุเพิ่งสร้าง) · มี 4-5 event · กำลังบันทึก · error · mobile
**ขอ variation:** ฟอร์มอยู่ล่าง timeline vs อยู่คนละคอลัมน์

## 4. จัดการบริษัทขนส่ง

ตาราง: ชื่อ · code · เว็บไซต์ · tracking URL template · toggle เปิด/ปิดใช้งาน · แก้ไข/ลบ
+ ฟอร์มเพิ่ม/แก้ไข

**จุดที่ต้องออกแบบให้ดี:** ช่อง `trackingUrlTemplate` ต้องใช้ placeholder `{trackingNumber}` เป๊ะๆ
ถ้าพิมพ์ผิดเป็นอย่างอื่น **ลิงก์ติดตามในอีเมลลูกค้าจะพังเงียบๆ** (เคยเกิดมาแล้วจริงในโปรเจกต์นี้)
ออกแบบให้พลาดยาก — เช่น live preview ว่าลิงก์จะออกมาหน้าตาแบบไหนเมื่อใส่เลขพัสดุตัวอย่าง

**ขอ state:** ตารางมีข้อมูล · ว่าง · ฟอร์มเพิ่ม · ฟอร์มแก้ไข · ยืนยันก่อนปิดใช้งาน (ขนส่งที่มีพัสดุค้างอยู่) · mobile

## 5. ระบบ badge ของ ShipmentStatus (ตารางอ้างอิง ไม่ใช่หน้าจอ)

ครบทั้ง 7 ค่า — ตอนนี้โปรเจกต์มีระบบสีสำหรับ `Order.status` แล้ว แต่**ยังไม่มีของ `ShipmentStatus`**
ขอชุดสีที่อยู่ในตระกูลเดียวกันแต่แยกออกจากกันได้ชัด โดย `failed`/`returned` ต้องอ่านออกทันทีว่าผิดปกติ
ใช้โครง badge เดียวกับของเดิม (12px/600, padding 5px 13px, radius 999px, จุดสี 6px)

## สิ่งที่ไม่ต้องทำ

- ไม่ต้องออกแบบ login/สิทธิ์ (มี `role: admin` อยู่แล้ว)
- ไม่ต้องมีกราฟ/dashboard ยอดขาย — หน้านี้คือ**เครื่องมือทำงาน** ไม่ใช่หน้ารายงาน
- ไม่ต้องมีปุ่มแก้ `Order.status` ตรงๆ — สถานะออเดอร์ขยับเองจากการบันทึกเหตุการณ์พัสดุ
