# นิยามหน้านี้ (อ่านก่อนออกแบบ)

ทะเบียนสมาชิก — **ดูเป็นหลัก สิ่งเดียวที่แก้ได้คือบทบาท (role)**

หน้านี้เนื้อหาน้อยที่สุดในชุดแอดมิน แต่ **เป็นหน้าที่พลาดแล้วเจ็บที่สุด** เพราะการกดผิดครั้งเดียวเปลี่ยนสิทธิ์คนได้จริง
เกณฑ์ตัดสินของหน้านี้จึงกลับด้านกับหน้าอื่น: **ดีไซน์ต้องทำให้ช้าลงและแน่ใจขึ้น ไม่ใช่เร็วขึ้น**

ระบบไม่มีรูปโปรไฟล์ ไม่มีเบอร์โทรในบัญชี ไม่มีประวัติการเข้าใช้ — อย่าเติมข้อมูลที่ไม่มี

# โครงหน้าที่ต้องออกแบบ

## 1. หัวหน้า

“จัดการผู้ใช้” + sub สั้นๆ
ตัวนับเป็นข้อความเรียบ **ไม่ใช่การ์ด KPI**: “สมาชิก 1,248 คน · แอดมิน 3 คน”
**ตัวเลขแอดมินต้องอยู่ตรงนี้เสมอ** เพราะมันคือบริบทของกฎ “ห้ามเหลือแอดมิน 0 คน”

## 2. แถบเครื่องมือ

ช่องค้นหา (ชื่อ / อีเมล) + **pill กรอง 4 อัน**: ทั้งหมด · แอดมิน · ลูกค้า · **ยังไม่ยืนยันอีเมล**
ต้องเห็นตลอดว่ากรองอะไรอยู่ และล้างได้ในคลิกเดียว

## 3. ตาราง

| คอลัมน์ | รายละเอียด |
|---|---|
| ผู้ใช้ | **avatar ตัวอักษรย่อในวงกลม 36px** พื้น `#ede9fe` ตัว `#6d28d9` `600` (ระบบไม่มีรูปโปรไฟล์) + ชื่อ `13.5px #1d1d1d` + อีเมล `12px #9ca3af` บรรทัดล่าง |
| บทบาท | chip — แอดมิน `#6d28d9`/`#ede9fe` · ลูกค้า `#6b7280`/`#f3f4f6` |
| อีเมล | ยืนยันแล้ว `#16a34a`/`#dcfce7` (มีติ๊กถูก) · ยังไม่ยืนยัน `#c2410c`/`#fff7ed`/ขอบ`#fed7aa` |
| วันที่สมัคร | วันที่ไทยแบบสั้น `13px` |
| — | ปุ่มเปลี่ยนบทบาท ชิดขวา |

**แถวของตัวเองต้องแยกออกจากแถวอื่นด้วยสายตา** — มีป้าย “คุณ” ต่อท้ายชื่อ
(จะเน้นพื้นแถวอ่อนๆ ด้วยก็ได้ แต่ห้ามใช้สีที่แรงกว่า chip ในตาราง)

**ห้ามใส่คอลัมน์อายุ** — ระบบมีข้อมูล `age` จริง แต่ไม่เกี่ยวกับงานแอดมินเลย

## 4. เปลี่ยนบทบาท — หัวใจของหน้านี้ ออกแบบให้ละเอียดที่สุดตรงนี้

**ปุ่มในตารางต้องบอกทิศทาง ไม่ใช่คำกลางๆ**
ลูกค้า → ปุ่ม “ตั้งเป็นแอดมิน” (ปุ่มรอง) · แอดมิน → ปุ่ม “ปลดเป็นลูกค้า” (ปุ่มอันตราย)
**ห้ามเป็น toggle หรือ dropdown ที่เปลี่ยนทันทีที่กด** ต้องผ่าน dialog ยืนยันเสมอ

**dialog ยืนยัน 2 แบบ แยกน้ำหนักกันชัดเจน:**

| | ขาขึ้น (ลูกค้า → แอดมิน) | ขาลง (แอดมิน → ลูกค้า) |
|---|---|---|
| น้ำหนัก | ยืนยันปกติ | **ต้องหนักกว่า** |
| ต้องบอกอะไร | อธิบายผลเป็นภาษาคน: “จะเข้าถึงหลังบ้านได้ทั้งหมด รวมถึงคำสั่งซื้อและข้อมูลผู้ใช้คนอื่น” | บอกว่าคนนี้จะเข้าหลังบ้านไม่ได้อีก และหลุดจากงานที่ค้างอยู่ |
| ปุ่มยืนยัน | ปุ่มหลักม่วง | ปุ่มแดงทึบ |

ทั้งสองแบบต้อง **ระบุชื่อและอีเมลของคนที่จะถูกเปลี่ยนให้ชัด** ไม่ใช่ “ยืนยันการเปลี่ยนบทบาท?” ลอยๆ

**สองกรณีที่ต้องกันไว้ล่วงหน้า (ห้ามรอให้กดแล้วค่อยขึ้น error):**
1. **แถวของตัวเอง** — ปุ่ม disabled พร้อมบอกเหตุผลตรงนั้น (“เปลี่ยนบทบาทของตัวเองไม่ได้”)
   ออกแบบมาว่าจะบอกยังไงให้เห็นโดยไม่ต้อง hover — mobile ไม่มี hover
2. **แอดมินคนสุดท้าย** — ปุ่มปลดต้อง disabled พร้อมเหตุผล (“ต้องมีแอดมินอย่างน้อย 1 คน”)

**แต่ก็ยังต้องออกแบบ error ตอนเซิร์ฟเวอร์ปฏิเสธด้วย** — เซิร์ฟเวอร์บังคับกฎทั้งสองข้อซ้ำอีกชั้น
(ปุ่มอาจ enabled อยู่เพราะข้อมูลในหน้าเก่าไปแล้ว เช่นแอดมินอีกคนถูกปลดไปพร้อมกัน)
เคสนี้ต้องขึ้นข้อความในตำแหน่งที่คนกำลังมองอยู่ — ใน dialog ที่เพิ่งกด ไม่ใช่ toast มุมจอ

**สถานะกำลังบันทึก** — ปุ่มยืนยัน disabled + สปินเนอร์ในปุ่ม กดซ้ำไม่ได้
เมื่อสำเร็จ chip บทบาทในแถวนั้นต้องเปลี่ยนทันทีและตัวนับ “แอดมิน N คน” ที่หัวหน้าต้องขยับตาม

## 5. ไม่มีปุ่มลบผู้ใช้ — ตั้งใจตัดออก

ผู้ใช้ผูกกับคำสั่งซื้อและที่อยู่ ลบแล้วประวัติการสั่งซื้อกำพร้า
ถ้าจะออกแบบ **“ระงับบัญชี”** ให้ทำเป็น **variation แยกพร้อมกำกับว่าเป็นเฟสถัดไป** — ระบบยังไม่มีฟิลด์รองรับ

## State ที่ขอ

- **มีข้อมูล** (desktop 1280) — ต้องเห็นในภาพเดียว: แถวแอดมิน · แถวลูกค้า · แถวที่ยังไม่ยืนยันอีเมล · **แถวของตัวเอง**
- **แอดมินเหลือคนเดียว** — ปุ่มปลดถูกล็อกพร้อมเหตุผล
- **dialog ยืนยันตั้งเป็นแอดมิน** · **dialog ยืนยันปลดเป็นลูกค้า** · **กำลังบันทึก**
- **เซิร์ฟเวอร์ปฏิเสธ** — ข้อความ error ใน dialog
- **ค้นหาไม่เจอ** — ต้องมีปุ่มล้างตัวกรอง
- **loading** — skeleton ทรงแถวตาราง **ห้าม spinner กลางจอ**
- **error โหลดข้อมูลไม่สำเร็จ** — แบนเนอร์แดง + ปุ่มลองใหม่
- **mobile 390** — ตารางเลื่อนแนวนอน + dialog เต็มจอ + เหตุผลของปุ่มที่ถูกล็อกต้องอ่านได้โดยไม่ต้อง hover

## ข้อมูลที่มีจริง (ห้ามใส่ฟิลด์ที่ไม่มีในนี้)

```
User   id, name, email, role('admin'|'customer'), emailVerified, age, createdAt
```

API ที่หน้านี้ใช้: `GET /users` (ทั้งหมด) · `PATCH /users/:id/role` (เปลี่ยนบทบาท — เป็น route เดียวที่แก้ role ได้)

## สิ่งที่ยังไม่มีในระบบ — ห้ามออกแบบ

- **ไม่มีรูปโปรไฟล์** (ใช้ตัวอักษรย่อเท่านั้น) · **ไม่มีเบอร์โทรในบัญชีผู้ใช้** (เบอร์อยู่ที่ที่อยู่จัดส่งของออเดอร์ คนละที่)
- **ไม่มีการเพิ่มผู้ใช้จากหน้าแอดมิน** — สมัครผ่านหน้าลูกค้าทางเดียว **ห้ามมีปุ่ม “+ เพิ่มผู้ใช้”**
- **ห้ามมีฟอร์มตั้ง/รีเซ็ตรหัสผ่านให้ผู้ใช้** — ระบบมี flow ลืมรหัสผ่านของเจ้าตัวอยู่แล้ว
- **ไม่มีการส่งอีเมลยืนยันซ้ำจากฝั่งแอดมิน** — เห็นได้ว่าใครยังไม่ยืนยัน แต่กดส่งซ้ำแทนเขาไม่ได้
- **ไม่มีการระงับ/แบนบัญชี** · **ไม่มี last login / ประวัติการเข้าใช้** · **ไม่มี audit log**
- **ไม่มีการเลือกหลายรายการ (bulk)** — ไม่มี checkbox เลือกหลายแถว
- **ไม่มีการแบ่งหน้าฝั่ง server** — ถ้าจะออกแบบ pagination ต้องเป็นแบบทำฝั่ง client
- **ไม่มีการส่งออก CSV/Excel**
- ไม่ต้องออกแบบ login/สิทธิ์ · **ไม่ต้องมีโหมดมืด**

## หมายเหตุถึงคนอิมพลีเมนต์ (ไม่ใช่โจทย์ดีไซน์)

- `PATCH /users/:id/role` รับ body `{ role: 'admin' | 'customer' }` และคืน user ที่อัปเดตแล้ว
- เซิร์ฟเวอร์บังคับกฎเองอยู่แล้ว — UI ที่ disable ปุ่มเป็นแค่ชั้นความสะดวก ต้องจับ error พวกนี้ให้ครบ:
  **403** = พยายามเปลี่ยนบทบาทตัวเอง · **409** = ปลดแอดมินคนสุดท้าย · **404** = ไม่พบผู้ใช้
- ตัวนับ “แอดมิน N คน” นับจากรายการที่โหลดมาแล้วฝั่ง client — ต้องอัปเดตหลังเปลี่ยนบทบาทสำเร็จทุกครั้ง
- `GET /users` และทุก route ใต้ `/users` เป็น **admin-only** แล้ว (`AuthGuard` + `RolesGuard`)
  → ผู้ใช้ที่ไม่ใช่แอดมินจะได้ 403 ไม่ใช่หน้าว่าง
- `createdAt` ถูกส่งออกมาจาก API แล้ว ใช้ทำคอลัมน์ “วันที่สมัคร” ได้เลย
- router guard เช็ค `meta.requiresAdmin` — หน้านี้ได้มาจาก parent route `/admin` อยู่แล้ว
