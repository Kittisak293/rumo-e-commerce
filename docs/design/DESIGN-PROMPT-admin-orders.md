# นิยามหน้านี้ (อ่านก่อนออกแบบ)

**ทะเบียนออเดอร์ไว้ค้นหาและตรวจย้อนหลัง** ไม่ใช่คิวงาน
ในระบบมีหน้า “คิวงานจัดส่ง” อยู่แล้ว จุดต่างต้องอ่านออกจากดีไซน์ ไม่ใช่รู้จากชื่อเมนู:

| | คิวงานจัดส่ง (มีแล้ว) | **หน้านี้** |
|---|---|---|
| เห็นออเดอร์ | เฉพาะ `paid·shipped·shipping·delivered` | **ครบทั้ง 9 สถานะ** |
| เรียงลำดับ | เก่าสุดขึ้นก่อน (ค้างนาน = เร่ง) | **ใหม่สุดขึ้นก่อน** |
| ทำอะไรได้ | สร้างพัสดุ / บันทึกเหตุการณ์ | **ดูอย่างเดียว** |

หน้านี้คือ **ที่เดียวในระบบที่มองเห็น** `pending` `processing` `failed` `cancelled` `refunded` —
ต้องออกแบบให้ตามหาสถานะพวกนี้เจอง่าย เพราะนั่นคือเหตุผลเดียวที่หน้านี้มีอยู่

⚠️ **ห้ามมีปุ่มหรือ dropdown แก้ `Order.status` เด็ดขาด** — สถานะขยับเองจาก webhook การชำระเงิน
และการบันทึกเหตุการณ์พัสดุเท่านั้น ถ้าออกแบบตัวแก้สถานะมา = ผิดโจทย์ทั้งหน้า

# โครงหน้าที่ต้องออกแบบ

## 1. หัวหน้า

“จัดการคำสั่งซื้อ” + sub “ทะเบียนคำสั่งซื้อทั้งหมด เรียงใหม่สุดขึ้นก่อน”
ขวามือเป็น **ตัวนับรวม** เช่น “ทั้งหมด 248 รายการ” — ข้อความเรียบ **ไม่ใช่การ์ด KPI** (หน้านี้ไม่ใช่แดชบอร์ด)

## 2. แถบเครื่องมือ

ช่องค้นหา (ค้นได้ด้วย **เลขคำสั่งซื้อ / ชื่อลูกค้า / อีเมล**) + ตัวกรองสถานะ

**โจทย์จริงของหน้านี้: 9 สถานะ ทำ pill เรียงแถวเดียวไม่พอ** ใช้ 2 ชั้น:

- **ชั้นบน — pill กลุ่ม 6 อัน** พร้อมตัวนับในแต่ละอัน:
  ทั้งหมด · รอชำระเงิน · กำลังเตรียม · กำลังจัดส่ง · สำเร็จ · มีปัญหา

  | กลุ่ม | สถานะดิบที่รวมอยู่ |
  |---|---|
  | รอชำระเงิน | `pending` |
  | กำลังเตรียม | `processing` + `paid` |
  | กำลังจัดส่ง | `shipped` + `shipping` |
  | สำเร็จ | `delivered` |
  | มีปัญหา | `failed` + `cancelled` + `refunded` |

  **กลุ่มชุดนี้ตรงกับที่ฝั่งลูกค้าใช้อยู่แล้ว ห้ามคิดกลุ่มใหม่**

- **ชั้นสอง — เจาะลงสถานะเดียว** (เช่นอยากหาเฉพาะ `refunded` ในกลุ่ม “มีปัญหา”)
  ออกแบบมา **2 ทางเลือกพร้อมบอกว่าอันไหนดีกว่าเพราะอะไร**:
  (ก) dropdown เลือกสถานะละเอียดข้างช่องค้นหา · (ข) pill ชั้นสองที่โผล่ใต้กลุ่มที่เลือกเท่านั้น

  ทางไหนก็ตาม ต้องเห็นได้ตลอดว่า **ตอนนี้กรองอะไรอยู่** และ **ล้างตัวกรองทั้งหมดได้ในคลิกเดียว**

## 3. ตาราง (ทรงเดียวกับคิวงานจัดส่ง)

| คอลัมน์ | รายละเอียด |
|---|---|
| เลขคำสั่งซื้อ | `600`, `white-space:nowrap` — รูปแบบจริงคือ `ORD-20260815-4821` (ยาว ต้องเผื่อความกว้าง) |
| ลูกค้า | ชื่อ `13.5px #1d1d1d` + อีเมล `12px #9ca3af` บรรทัดล่าง |
| วันที่สั่ง | วันที่ไทยแบบสั้น + เวลา (`13px`) |
| ชิ้น | `totalQuantity` |
| ยอดรวม | `600 #6d28d9`, `nowrap` |
| สถานะ | badge ตามชุดสี 9 ค่าข้างบน |
| — | ปุ่มรอง “ดูรายละเอียด” ชิดขวา |

**เรียงใหม่สุดขึ้นก่อนเสมอ** — ไม่ต้องมีตัวเลือกเรียงลำดับ (ถ้าคิดว่าจำเป็นให้เสนอเป็น variation แยก พร้อมเหตุผล)

## 4. แผงรายละเอียด — **side drawer เลื่อนเข้ามาจากขวา**

ไม่ใช่หน้าใหม่ ไม่ใช่ modal กลางจอ เพราะแอดมินไล่เปิดดูทีละหลายออเดอร์
ต้องกลับมาที่ตารางเดิมได้โดยไม่เสียตำแหน่งเลื่อนและไม่เสียตัวกรองที่ตั้งไว้

ข้างในเรียงตามนี้:
1. เลขคำสั่งซื้อ + badge สถานะ + วันที่สั่ง + ปุ่มปิด
2. **ลูกค้า** — ชื่อ + อีเมล
3. **ที่อยู่จัดส่ง** — ชื่อผู้รับ · เบอร์ · ตำบล/อำเภอ/จังหวัด/รหัสไปรษณีย์
4. **รายการสินค้า** — รูปเล็ก (44px radius 10) + ชื่อ · `ราคา × จำนวน` · ยอดต่อรายการชิดขวา
5. **สรุปยอด** — ยอดสินค้า · ค่าจัดส่ง · **ยอดรวม** (เน้น `#6d28d9`)
6. **พัสดุ** — ถ้ามี: เลขพัสดุ · บริษัทขนส่ง · สถานะพัสดุ · ปุ่มไปหน้าติดตาม
   ถ้าไม่มี: ต้องบอกตรงๆ ว่า “ยังไม่มีพัสดุ” + ลิงก์ไปคิวงานจัดส่ง (ไม่ใช่ปล่อยว่าง)

⚠️ ในแผงนี้ก็ยัง **ห้ามมีปุ่มแก้สถานะ / ยกเลิกออเดอร์ / คืนเงิน** — ระบบไม่มี flow พวกนี้เลย

## ข้อมูลที่มีจริง (ห้ามใส่ฟิลด์ที่ไม่มีในนี้)

```
Order      orderNumber, status(9 ค่า), subtotal, shippingFee, total, totalQuantity,
           createdAt, updatedAt, user, address
OrderItem  product(name, imageUrl), price, quantity, lineTotal
Address    fullName, phone, subdistrict, district, province, postalCode   ← ไม่มีบ้านเลขที่เป็นฟิลด์แยก
Shipment   trackingNumber, status(7 ค่า: pending·picked_up·in_transit·out_for_delivery·delivered·failed·returned),
           lastLocation, estimatedDeliveryAt, carrier(name, code)
User       name, email                                                    ← ไม่มีรูปโปรไฟล์ ไม่มีเบอร์ในโปรไฟล์
```

## สิ่งที่ยังไม่มีในระบบ — ห้ามออกแบบ

- **ไม่มีการแก้สถานะออเดอร์ด้วยมือ** — ไม่มี endpoint ไม่มีปุ่ม ไม่มี dropdown
- **ไม่มีการยกเลิกออเดอร์ฝั่งแอดมิน** และ **ไม่มีระบบคืนเงิน/คืนสินค้า** (`refunded` ค้นเจอได้แต่กดไม่ได้)
- **ไม่มีข้อมูลการชำระเงินให้แสดง** — มีแค่ `stripePaymentIntentId` เป็นสตริง ไม่มีวิธีจ่าย/บัตร/สลิป
- **ไม่มีหมายเหตุ/โน้ตในออเดอร์** ไม่มีแชทกับลูกค้า ไม่มีการส่งอีเมลจากหน้านี้
- **ไม่มี audit log** — ห้ามมี “ใครทำอะไรกับออเดอร์นี้เมื่อไหร่”
- **ไม่มีการแบ่งหน้าฝั่ง server** — ถ้าจะออกแบบ pagination ต้องเป็นแบบทำฝั่ง client
- **ไม่มีการส่งออก CSV/Excel** และ **ไม่มีการพิมพ์ใบเสร็จ/ใบปะหน้ากล่อง**
- **ไม่มีระบบร้านค้า/ผู้ขายรายราย** — `storeType` เป็นแค่ป้ายข้อมูลบนสินค้า ไม่ใช่เจ้าของ
- ไม่ต้องออกแบบ login/สิทธิ์ · **ไม่ต้องมีโหมดมืด**

## หมายเหตุถึงคนอิมพลีเมนต์ (ไม่ใช่โจทย์ดีไซน์)

- **`GET /orders` (admin) โหลด relation แค่ `user`, `address`** — ไม่มี `orderItems`/`shipments`
  และ **ไม่ได้เรียงลำดับมาให้เลย** → ตารางต้องเรียงใหม่สุดขึ้นก่อนเองฝั่ง client
- **ยังไม่มี endpoint ให้แอดมินเปิดออเดอร์ของลูกค้าคนอื่น** — `GET /orders/:id` คือ `findOneForUser(id, req.user.sub)`
  ซึ่งผูกกับเจ้าของออเดอร์ แอดมินเปิดจะได้ **404** → ต้องเพิ่ม `GET /orders/admin/:id`
  (relation: `user, address, orderItems, orderItems.product, shipments, shipments.carrier`) ก่อนแผงรายละเอียดจะทำงานได้จริง
- ห้ามดึงรายละเอียดจาก `GET /orders/admin/shipping-queue` แทน — queue นั้นไม่มี `pending·failed·cancelled·refunded`
  ซึ่งเป็นออเดอร์กลุ่มที่หน้านี้ตั้งใจให้เปิดดู
- `Order.total` / `subtotal` / `shippingFee` / `OrderItem.lineTotal` เป็น `decimal` → `pg` คืนมาเป็น **string**
  ต้อง `Number()` ก่อนคำนวณหรือจัดรูปแบบ
- router guard เช็ค `meta.requiresAdmin` — หน้านี้ได้มาจาก parent route `/admin` อยู่แล้ว
