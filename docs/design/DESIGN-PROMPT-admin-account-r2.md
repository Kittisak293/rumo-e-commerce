# หน้าจอที่ต้องออกแบบ

## 1. จัดการคำสั่งซื้อ (`/admin/orders`)

ทะเบียนออเดอร์ทั้งหมดไว้ **ค้นหาและตรวจสอบย้อนหลัง** — ต่างจากหน้า “จัดการพัสดุ” ที่เป็นคิวงานให้ลงมือ

- ตารางทุกออเดอร์ เรียง **ใหม่สุดขึ้นก่อน** (ตรงข้ามกับหน้าพัสดุที่เรียงเก่าสุดก่อน)
- คอลัมน์: เลขคำสั่งซื้อ · ลูกค้า (ชื่อ+อีเมล) · วันที่สั่ง · จำนวนชิ้น · ยอดรวม · badge สถานะ
- ค้นหาด้วยเลขคำสั่งซื้อหรืออีเมลลูกค้า + กรองสถานะครบ **ทั้ง 9 ค่า**
  จุดสำคัญ: หน้านี้คือที่เดียวที่เห็นออเดอร์ `pending` `failed` `cancelled` `refunded` ซึ่งคิวพัสดุมองไม่เห็นเลย
- กดแถวแล้วดูรายละเอียด (สินค้าในออเดอร์ · ที่อยู่จัดส่ง · พัสดุถ้ามี)

⚠️ **ห้ามมีปุ่มแก้ `Order.status` ตรงๆ** — สถานะขยับเองจาก webhook การชำระเงินและการบันทึกเหตุการณ์พัสดุเท่านั้น
หน้านี้ **ดูอย่างเดียว** ถ้าออกแบบปุ่มแก้สถานะมา = ผิดโจทย์

**ขอ state:** มีข้อมูล · ค้นหาไม่เจอ · loading (skeleton ทรงตาราง) · mobile 390

## 2. จัดการสินค้า (`/admin/products`)

- ตาราง: รูป · ชื่อ · หมวดหมู่ · `storeType` (`mall`/`seller` — เป็นแค่ป้ายกำกับ ไม่ใช่เจ้าของร้าน) · ราคา · สต็อก · แก้ไข/ลบ
- ฟอร์มเพิ่ม/แก้ไข + อัปโหลดรูป (**หลายรูปต่อสินค้า มีรูปหลัก 1 รูป**)
- สินค้าสต็อกใกล้หมด/หมด ต้องอ่านออกทันทีจากในตาราง

หมายเหตุ: สินค้า 1 ตัวมีหลาย SKU จากตัวเลือก (สี/ไซซ์) — ถ้าจะออกแบบตัวจัดการ SKU
ให้ทำเป็น **variation แยก** พร้อมระบุว่าเป็นงานเฟสถัดไป อย่ายัดรวมกับฟอร์มหลัก

**ขอ state:** ตารางมีข้อมูล · ว่าง · ฟอร์มเพิ่ม · ฟอร์มแก้ไข · mobile 390

## 3. จัดการหมวดหมู่ (`/admin/categories`)

เล็กที่สุดใน 4 หน้า — รายการหมวดหมู่ + รูปหมวด + เพิ่ม/แก้ชื่อ/เปลี่ยนรูป/ลบ
ต้องมี **ยืนยันก่อนลบหมวดที่ยังมีสินค้าอยู่** (บอกจำนวนสินค้าที่กระทบ)

**ขอ state:** มีข้อมูล · ว่าง · ฟอร์ม · ยืนยันลบ · mobile 390

## 4. จัดการผู้ใช้ (`/admin/users`)

- ตาราง: ชื่อ · อีเมล · role (`admin`/`customer`) · ยืนยันอีเมลแล้วหรือยัง · วันที่สมัคร
- เปลี่ยน role ได้
- ค้นหาด้วยชื่อ/อีเมล

⚠️ ต้องออกแบบกันพลาด: **แอดมินปลดสิทธิ์ตัวเองไม่ได้** (ปุ่มของแถวตัวเองต้องถูกล็อกพร้อมบอกเหตุผล)
และการเปลี่ยนใครเป็นแอดมินต้องมีจังหวะยืนยัน ไม่ใช่ toggle ติดปุ๊บ

**ขอ state:** มีข้อมูล · แถวของตัวเอง (ล็อก) · ยืนยันตั้งเป็นแอดมิน · mobile 390

## ข้อมูลที่มีจริง (ห้ามใส่ฟิลด์ที่ไม่มีในนี้)

```
User      name, email, role('admin'|'customer'), emailVerified, createdAt   ← ไม่มีรูปโปรไฟล์, ไม่มีเบอร์
Order     orderNumber, status(9 ค่า), total, totalQuantity, subtotal, createdAt, updatedAt
Address   fullName, phone, subdistrict, district, province, postalCode
OrderItem product.name, product.imageUrl, price, quantity, lineTotal
Product   name, description, price, stock, storeType('mall'|'seller'), ratingAvg, images[], category
Category  name, imageUrl
```

## สิ่งที่ยังไม่มีในระบบ — อย่าออกแบบ

- **ไม่มีข้อมูลยอดขาย/กราฟ/รายงาน** — อย่าใส่กราฟรายได้ ยอดขายรายวัน หรือ KPI การเงินในหน้าไหนก็ตาม
- **ไม่มีระบบร้านค้า/ผู้ขายรายราย** — `storeType` เป็นแค่ป้ายข้อมูล ไม่ใช่เจ้าของ
- **ไม่มีระบบคืนเงิน/คืนสินค้า** — `refunded` เป็นสถานะที่ไปถึงได้ แต่ไม่มี flow ให้กด
- **ไม่มีรีวิว/แชท/ระบบส่งการแจ้งเตือนหาลูกค้า**
- **ไม่มีประวัติการแก้ไข (audit log)** — อย่าออกแบบ “ใครแก้อะไรเมื่อไหร่”
- ไม่ต้องออกแบบ login/สิทธิ์ · ไม่ต้องมีโหมดมืด

## หมายเหตุถึงคนอิมพลีเมนต์ (ไม่ใช่โจทย์ดีไซน์)

- `GET /users`, `POST/PATCH/DELETE /products`, `/category` **ยังไม่มี `RolesGuard`**
  (`/users` มีแค่ `AuthGuard`, products/categories เปิดโล่งไม่มี auth เลย)
  **ต้องใส่ `@UseGuards(AuthGuard, RolesGuard) @Roles('admin')` ก่อนทำ 3 หน้านี้จริง**
- router guard ปัจจุบันเช็ค `meta.requiresAdmin` — ทุกหน้าใหม่ต้องติด meta นี้
