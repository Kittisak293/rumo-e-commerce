# นิยามหน้านี้ (อ่านก่อนออกแบบ)

หน้าที่เล็กที่สุดในชุดแอดมิน — **ทั้งหมวดหมู่มีแค่ 2 อย่างที่แก้ได้: ชื่อ กับ รูป**
(อีกฟิลด์คือ `slug` ซึ่งระบบสร้างเอง — รายละเอียดอยู่ในหัวข้อ “slug” ด้านล่าง ต้องอ่าน)

งานที่แอดมินมาทำมี 3 อย่างเท่านั้น: **เพิ่มหมวด · แก้ชื่อ/เปลี่ยนรูป · ลบหมวด**
ความยากทั้งหมดของหน้านี้อยู่ที่ **การลบ** เพราะระบบไม่มีอะไรกันเลย

## ทำไมหน้านี้ใช้ grid การ์ด ไม่ใช่ตาราง

อีก 3 หน้าแอดมิน (พัสดุ/คำสั่งซื้อ/สินค้า) ใช้ตาราง หน้านี้ **ตั้งใจใช้ grid การ์ด** เพราะ:
- หมวดหมู่มีแค่ 2 ฟิลด์ — ตาราง 2 คอลัมน์จะโล่งเวิ้งครึ่งจอ
- **รูปหมวดคือของที่ต้องตรวจด้วยตา** มันไปโผล่หน้าแรกของร้าน รูปเล็ก 44px ในตารางดูไม่ออกว่ารูปถูกหรือเปล่า

ถือว่านี่เป็นข้อยกเว้นที่ตัดสินแล้ว **ไม่ต้องเสนอเวอร์ชันตารางมาเทียบ** — แต่ทุกอย่างที่เหลือ
(สี ปุ่ม radius เงา ฟอร์ม dialog สถานะ) ต้องเหมือนหน้าอื่นเป๊ะ

# โครงหน้าที่ต้องออกแบบ

## 1. หัวหน้า

“จัดการหมวดหมู่” + sub สั้นๆ · ตัวนับ “ทั้งหมด 12 หมวด” เป็นข้อความเรียบ **ไม่ใช่การ์ด KPI**
ขวาสุด: **ปุ่มหลัก “+ เพิ่มหมวดหมู่”**

## 2. แถบค้นหา

ช่องค้นหาชื่อหมวดอย่างเดียว — **ไม่ต้องมี pill filter** (ไม่มีอะไรให้กรอง หมวดหมู่ไม่มีสถานะ)
ถ้ามองว่าจำนวนหมวดน้อยจนช่องค้นหาไม่จำเป็น ให้เสนอมาได้พร้อมเหตุผล แต่ต้องเผื่อกรณีมี 30–40 หมวด

## 3. Grid การ์ดหมวดหมู่

การ์ดละหมวด `border-radius:18px` เงาชุดเดียวกับการ์ดอื่น · desktop 3–4 ใบต่อแถว · mobile 1 ใบ

ในการ์ดมี:
- **รูปหมวด** — สัดส่วนคงที่ (เสนอ 16:9 หรือ 4:3 เลือกมาแบบเดียว) `object-fit:cover` มุมบนโค้งตามการ์ด
- **ชื่อหมวด** `15px/600 #1d1d1d`
- **จำนวนสินค้าในหมวด** — chip ตัวนับ เช่น “47 สินค้า”
  **ข้อมูลชิ้นนี้ขาดไม่ได้** เพราะมันคือสิ่งเดียวที่ทำให้แอดมินตัดสินใจลบได้อย่างรู้ตัว
  หมวดที่มี **0 สินค้า** ต้องอ่านออกว่าว่าง (โทนจาง `#9ca3af`)
- **ปุ่มแก้ไข (ปุ่มรอง) + ปุ่มลบ (ปุ่มอันตราย)**

**ต้องออกแบบกรณีรูปพัง/ไม่มีรูปด้วย** — ระบบตั้งค่าเริ่มต้นเป็น `unknown.jpg` ให้เอง
หมวดที่ยังใช้รูปเริ่มต้นควรอ่านออกว่า “ยังไม่ได้ใส่รูป” ไม่ใช่ปล่อยให้ดูเหมือนรูปจริง

## 4. ฟอร์มเพิ่ม / แก้ไข — **dialog**

เข้าชุดกับ dialog ที่โปรเจกต์มีอยู่แล้ว (`CreateShipmentDialog`, `AddShipmentEventDialog`)
กว้างประมาณ 480px (เล็กกว่าฟอร์มสินค้าเพราะมี 2 ฟิลด์) · หัว dialog + ปุ่มปิด · ปุ่ม “ยกเลิก / บันทึก” ล่างขวา

| ฟิลด์ | ชนิด |
|---|---|
| ชื่อหมวดหมู่ | text — **บังคับกรอก** |
| รูปหมวดหมู่ | drop zone + พรีวิว + ปุ่มเปลี่ยนรูป (**รูปเดียว**) |

ต้องออกแบบ:
- **drop zone 3 สถานะ** — ยังไม่มีรูป / มีพรีวิวแล้ว / กำลังอัปโหลด
- **ฟอร์มแก้ไขต้องโชว์รูปเดิมเป็นพรีวิวมาก่อน** และต้องชัดว่าถ้าไม่เลือกไฟล์ใหม่ รูปเดิมจะไม่ถูกแตะ
- **สถานะกำลังบันทึก** — ปุ่ม disabled + สปินเนอร์ในปุ่ม กดซ้ำไม่ได้

## 5. slug — สิ่งที่ต้องตัดสินใจในดีไซน์ ห้ามข้าม

ระบบสร้าง `slug` จากชื่อให้อัตโนมัติ **ตอนสร้างครั้งแรกเท่านั้น** (พิมพ์เล็ก + ช่องว่างกลายเป็นขีด)
และคอลัมน์นี้ **ห้ามซ้ำ** ทั้งตาราง ผลที่ตามมา 2 ข้อที่ดีไซน์ต้องรับมือ:

1. **ตั้งชื่อซ้ำกับหมวดที่มีอยู่ = บันทึกไม่ผ่าน** → ต้องมี **error รายฟิลด์ใต้ช่องชื่อ** (“ชื่อนี้มีอยู่แล้ว”)
   ไม่ใช่ toast ลอยมุมจอ
2. **แก้ชื่อทีหลัง slug ไม่เปลี่ยนตาม** → เปลี่ยน “เสื้อผ้า” เป็น “แฟชั่น” แล้ว URL ยังเป็นของเดิม

ข้อ 2 ต้องเลือกทางใดทางหนึ่งแล้วบอกเหตุผล:
- **(แนะนำ)** โชว์ slug ในฟอร์มแก้ไขแบบ **อ่านอย่างเดียว** + ข้อความกำกับว่าลิงก์เดิมไม่เปลี่ยนตามชื่อ
- ให้แก้ slug ได้เอง (ต้องมี error “ซ้ำ” แบบเดียวกับชื่อ และต้องเตือนว่าลิงก์เดิมจะใช้ไม่ได้)
- ไม่โชว์เลย (ต้องอธิบายว่าทำไมการซ่อนดีกว่า)

## 6. ลบหมวดหมู่ — จุดอันตรายจริงของหน้านี้

**ระบบหลังบ้านไม่เช็คอะไรเลย** — สั่งลบหมวดที่มีสินค้า 47 ชิ้นก็ลบทันที สินค้ากลายเป็นสินค้าไร้หมวด
**หน้าจอนี้คือด่านเดียวที่กันได้** ต้องออกแบบยืนยันลบ **2 แบบแยกกันชัดเจน**:

| กรณี | สิ่งที่ต้องเห็น |
|---|---|
| **หมวดว่าง (0 สินค้า)** | dialog ยืนยันธรรมดา ระบุชื่อหมวด กดยืนยันจบ |
| **หมวดมีสินค้า** | ต้องบอก **จำนวนสินค้าที่กระทบ** และบอกว่าจะเกิดอะไรขึ้นกับสินค้าเหล่านั้น + ทางออก (ย้ายหมวดก่อน) |

กรณีที่สองให้เสนอมา **2 ทางพร้อมข้อดีข้อเสีย**: บล็อกไปเลยจนกว่าจะย้ายสินค้าออก vs ให้ลบได้แต่ต้องยืนยันหนักขึ้น
ถ้อยคำต้องตรงกับพฤติกรรมจริง: **หมวดจะหายจากหน้าร้านทันที และหน้านี้ไม่มีทางกู้คืน**

---

## State ที่ขอ

- **มีข้อมูล** (desktop 1280) — ต้องมีทั้งหมวดที่มีสินค้าเยอะ หมวดที่มี 0 สินค้า และหมวดที่ยังไม่ได้ใส่รูป ในภาพเดียว
- **ยังไม่มีหมวดหมู่เลย** — empty ที่พาไปสร้างหมวดแรก
- **ค้นหาไม่เจอ** (ถ้าออกแบบช่องค้นหา)
- **loading** — skeleton ทรงการ์ดจริง **ห้าม spinner กลางจอ**
- **error** — แบนเนอร์แดง + ปุ่มลองใหม่
- **dialog เพิ่ม** (ว่าง) · **dialog แก้ไข** (มีชื่อเดิม + รูปเดิม) · **กำลังอัปโหลดรูป** · **error ชื่อซ้ำ**
- **dialog ยืนยันลบ — ทั้งแบบหมวดว่างและแบบมีสินค้า**
- **mobile 390** — การ์ด 1 ใบต่อแถว + dialog เต็มจอ

## ข้อมูลที่มีจริง (ห้ามใส่ฟิลด์ที่ไม่มีในนี้)

```
Category   name, slug, imageUrl
```

จำนวนสินค้าต่อหมวด **ไม่มี endpoint ให้** ต้องนับเองฝั่ง frontend จาก `GET /products` (ซึ่งคืน `category` มาด้วยอยู่แล้ว)

## สิ่งที่ยังไม่มีในระบบ — ห้ามออกแบบ

- **ไม่มีลำดับการแสดงผล** — ไม่มีฟิลด์ `sortOrder` → **ห้ามออกแบบการลากสลับตำแหน่งการ์ด**
- **ไม่มีหมวดย่อย/ลำดับชั้น** — ไม่มีฟิลด์ parent → ห้ามมี tree, ห้ามมี “หมวดแม่/หมวดลูก”
- **ไม่มีคำอธิบายหมวด** ไม่มีไอคอนหมวด ไม่มีสีประจำหมวด
- **ไม่มีสถานะเปิด/ปิดการแสดงผล** — ลบคือ soft delete ล้วน ไม่มีการซ่อนชั่วคราว
- **ไม่มีการย้ายสินค้าข้ามหมวดจากหน้านี้** — ต้องไปทำที่หน้าจัดการสินค้า (ลิงก์ไปได้ แต่อย่าออกแบบตัวย้ายที่นี่)
- **ไม่มี SEO fields** (meta title/description) ไม่มีแบนเนอร์หมวด
- **ไม่มีการเลือกหลายรายการ (bulk)** ไม่มี audit log ไม่มีการแบ่งหน้าฝั่ง server
- ไม่ต้องออกแบบ login/สิทธิ์ · **ไม่ต้องมีโหมดมืด**

## หมายเหตุถึงคนอิมพลีเมนต์ (ไม่ใช่โจทย์ดีไซน์)

- **`DELETE /category/:id` ไม่เช็คสินค้าในหมวดเลย** (`CategoryService.remove` = `softDelete` ล้วน)
  ด่านกันทั้งหมดอยู่ที่ UI — ถ้าจะให้ปลอดภัยจริงควรเพิ่มการเช็คฝั่ง server ด้วย
- **ชื่อฟิลด์ไฟล์ต้องเป็น `imageUrl`** — controller ใช้ `FileInterceptor('imageUrl')`
  แต่ `categoryStore` ปัจจุบัน `formData.append('file', file)` → **ไฟล์ถูกทิ้งเงียบๆ หมวดได้รูป `unknown.jpg` ตลอด** ต้องแก้
- **`CreateCategoryDto` บังคับส่ง `slug` มาด้วย** (`@IsString()` ไม่ optional) ทั้งที่ service เขียนทับด้วยค่าที่สร้างจากชื่ออยู่ดี
  และ `main.ts` เปิด `ValidationPipe({ whitelist: true })` → `POST /category` ที่ส่งแค่ `name` จะ **400**
  ควรแก้ DTO ให้ `slug` เป็น optional แทนที่จะให้ frontend ส่งค่าหลอกไป
- **`CategoryService.update` ไม่สร้าง slug ใหม่จากชื่อ** แต่ **จะเขียน slug ถ้า client ส่งมา** —
  ถ้าเลือกทาง “แก้ slug ได้” ในดีไซน์ ก็ทำได้เลยโดยไม่ต้องแก้ backend (แต่ต้องจับ error ซ้ำ)
- `slug` เป็น `unique` และไม่มีการแปลงภาษาไทยเป็นอักษรโรมัน — ชื่อไทยจะได้ slug ไทย ใช้งานได้แต่ URL จะเป็นภาษาไทย
- **`/category` ทั้ง controller ไม่มี auth เลยสักชั้น** — ใครก็ยิง `POST`/`PATCH`/`DELETE` ได้
  **ต้องใส่ `@UseGuards(AuthGuard, RolesGuard) @Roles('admin')` ที่ route เขียนข้อมูลก่อนปล่อยหน้านี้ขึ้นจริง**
  (`GET` เปิดไว้ได้ หน้าร้านฝั่งลูกค้าใช้อยู่)
- router guard เช็ค `meta.requiresAdmin` — หน้านี้ได้มาจาก parent route `/admin` อยู่แล้ว
